# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

The project concept lives in `doc/PROJEKTIDEE.md` (German). Implementation is a generic, config-driven pipeline engine (`archivlotse/pipeline.py: process_step`) with eight step shapes:

- **Text steps** (e.g. `title`): read one Paperless field, run it through a prompt + AI model, write the cleaned-up free-text result to another Paperless field.
- **Choice steps** (e.g. `document_type`): same, but the AI must pick one value out of an existing Paperless list (fetched live via the Paperless API), and a suggestion that doesn't match an existing candidate is rejected rather than written. This is the first bit of the concept doc's "validate before writing" / "never invent new metadata objects" principle actually implemented.
- **Multi-choice steps** (e.g. `tags`, `candidates_endpoint` + `multi: true`): like a choice step, but for a many-to-many Paperless field (a list of ids, not a scalar FK). The AI may suggest several comma-separated candidates; each is validated independently (an invalid one is dropped with a warning, not fatal to the whole step), and the valid ones are **added** to the field's current values — existing values (e.g. manually-set tags) are never removed.
- **OCR step** (`ocr`, step has an `ocr: {model: ...}` block): no prompt — scanned documents are transcribed by an OCR engine named like any other model in `config/ai.yaml`, and the result replaces `content`. Default (user's choice, 2026-10-26) is `docling`: a local Docling Serve (provider `type: docling`, `archivlotse/ai/docling.py`, `force_ocr`, plain-text output, $0); the alternative `lightonocr-3-0.8b` on Scaleway is selected just by changing `ocr.model` (or `--model`). Side-by-side tests (docs 5271, 5743): LightOnOCR was clearly best on tables, Docling's RapidOCR gets the characters right but merges/breaks table rows (lost a bank-statement booking line on 5743), Tesseract misread digits, general vision LLMs like `mistral-small` silently "corrected" digits such as a postal code — don't offer those as OCR engines. Scaleway's LightOnOCR sometimes took 3 minutes for one page. Whether to OCR is decided **structurally, never by a text-quality metric** (`archivlotse/pdf_text.py: analyze_pdf`): a PDF original is OCR'd only if at least one page shows an image but no *visible* text (text in render mode 3 — the invisible OCR layer scanner apps and Paperless' OCRmyPDF put over a scan — doesn't count); a born-digital PDF is never touched. Image originals are always OCR'd, sent as Paperless' archived PDF (Scaleway's OCR endpoint only accepts PDFs); other originals (e-mail, text, office) are skipped. This is the concept doc's "Schritt 1: Dokumentprüfung und OCR". Known gap (LightOnOCR): it sometimes treats a phone photo of a receipt as a picture and returns only an image placeholder or a fragment (e.g. doc 10400) — the post-OCR length check keeps the existing text then; accepted as an exception, not fixed.
- **Correspondent step** (`correspondent`, step has `prompt_step2` set): two-stage recognition against Paperless's ~1000 correspondents (`config/prompts/correspondent-step1.j2`/`correspondent-step2.j2`; decision rules and threshold rationale are commented next to `fuzzy_*` in `config/steps.yaml`). Step1 (AI) extracts a probable name from the text; RapidFuzz then scores it deterministically against every existing correspondent (no AI); a confident, clearly-leading fuzzy match is assigned directly, an ambiguous one (several similarly-plausible candidates) triggers step2 (AI, given only the closest few candidates) to disambiguate using the full text, and a weak match is left alone. In `pipeline:` since 2026-10-11, between `document_type` and `tags` (thresholds are still example starting values, not yet calibrated against a larger document sample). Design rules worth keeping when touching this: name normalization before fuzzy matching is deliberately minimal (`_normalize_correspondent_name`: whitespace + casefold only) — legal forms, location suffixes and terms like "Lebensversicherung" vs. "Versicherung" can mark genuinely different legal entities and must not be normalized away; a high score alone is not proof of identity (a mediocre top score with a large gap goes to step2, never straight to auto-assignment); step2 gets only the closest `fuzzy_candidate_limit` candidates scoring ≥ `fuzzy_review_min_score` and its answer is accepted only as an exact candidate name — anything else is a new-correspondent proposal, never an id lookup by similarity. A wrong merge is costlier than an unassigned document. A correspondent name step2 proposes that matches none of its candidates is logged as a new-correspondent proposal and never auto-created. Known gap: on a Kontoauszug (no clear sender/recipient letterhead), step1 often returns `KEINEN-GEFUNDEN` instead of the issuing bank — not yet fixed.
- **Date step** (`document_date`, step has a `date:` block with `prompt_small` set, `target_field: created`): `_process_date_step`. Text ≤ `date.small_max_chars` (8000) → one call with `create-date-small.j2` (answer `DD.MM.YYYY`, no score), a valid date is applied. Longer → first `date.part_chars` (6000) with `prompt` (`create-date-part.j2`, answer `DD.MM.YYYY|SCORE`); score ≥ `date.min_score` (85) is applied without a second call, otherwise the last 6000 chars are also asked and the valid date with the highest score wins. A best score < 85 is only written if the target field is empty (never overwrites an existing date). `_parse_date_answer` validates every answer (exact format via fullmatch, real calendar date, not in the future, year ≥ `MIN_DOCUMENT_YEAR` 1900, score 1–100); anything else, or `KEIN-DATUM-GEFUNDEN`, counts as no date. Each AI call is cached separately (`step_results.step_name` = `document_date:small`/`:first`/`:last`). The old value is compared as `str(created)[:10]` since Paperless returns either a date or a full ISO datetime depending on version; the written value is `YYYY-MM-DD`. Known gap: a date in the middle of a long document isn't found (no passage search yet).
- **Custom-field step** (`geldbetrag`, step has `custom_field` set; `target_field` defaults to and must be `custom_fields`): `_process_custom_field_step`. Looks the field up by name via the cached `_get_candidates(conn, paperless, "custom_fields")` (forced re-fetch once if missing, then raises — never auto-created). Skips before any AI call if `condition:` fails or the field already has a value and `overwrite_existing` is false (default). Otherwise a text-step-style AI call (prompt also gets `{{ field_name }}`, fingerprint includes field name + data type), and `_parse_custom_field_answer` validates the answer against the field's `data_type` (`string`/`longtext` as-is, `integer`/`float` a plain number with `.` or `,` decimal and no thousands separators, `monetary` additionally an optional 3-letter currency code → `"EUR12.50"`; `KEIN-WERT` or a wrong-type answer writes nothing; other data types raise). The write sends the document's **whole** `custom_fields` list with only this field replaced/added, so other custom fields survive regardless of Paperless's PATCH semantics; audited as `custom_field:<name>`. `geldbetrag` fills the float field `Geldbetrag` only for `document_type: [Rechnung, Quittung]` (`condition:` values may now be a list of allowed values); `rechnungsnummer` fills the string field `Rechnungsnummer` only for `Rechnung` (pipeline: right after `geldbetrag`; batch job `rechnungsnummer` = Rechnungen with `Geldbetrag` filled and `Rechnungsnummer` missing).
- **Add-tags step** (`mark_done`, step has `add_tags` set, `target_field: tags`): no AI, no source field, no fingerprint/cache — adds fixed, already existing tags by name (`_process_add_tags_step`, union with the current tags, existing ones kept, audited via `_apply_value`). A named tag missing from Paperless raises (after one forced re-fetch of the cached tag list, so a tag created just now is found); it is never auto-created. `mark_done` adds `archivlotse-done`, is the last entry in `pipeline:`, and is also in the `tags` step's `protected_candidates` so the AI can't remove it again.

All shapes are driven by `config/steps.yaml`, with no step-specific Python code for ordinary cases. A `pipeline:` list in the same file defines the step order; `archivlotse process <id>` (no `--step`) runs them all via `process_pipeline`, with a failing step logged and skipped rather than aborting the rest. Text/choice/multi-choice/correspondent steps also support an optional `condition:` (skip the step unless the document's current field — currently only `document_type`, resolved by name — matches), and every prompt render additionally receives `{{ document_type_name }}`, so e.g. `title.j2` can branch its instructions by document type. Candidate lists (document types, tags, correspondents) are cached in SQLite for `CANDIDATE_CACHE_TTL_SECONDS` (2h) across separate CLI invocations, via `_get_candidates()` — `CANDIDATE_FETCHERS` entries should always be called through that, never directly, or caching is silently bypassed.

Currently defined steps/models, in `pipeline:` order: `ocr` (scans only, local Docling; Scaleway `lightonocr-3-0.8b` as config alternative), `document_type` (OCR text → document type, Scaleway `mistral-small-3.2-24b-instruct-2506`), `correspondent` (OCR text → correspondent, two-stage: Scaleway `mistral-small-3.2-24b-instruct-2506` for step1 + RapidFuzz, Scaleway `llama-3.3-70b-instruct` for step2), `document_date` (OCR text → `created`, Scaleway `mistral-small-3.2-24b-instruct-2506`), `geldbetrag` (OCR text → custom field `Geldbetrag`, only Rechnung/Quittung, Scaleway `mistral-small-3.2-24b-instruct-2506`), `rechnungsnummer` (OCR text → custom field `Rechnungsnummer`, only Rechnung, same model), `tags` (OCR text → tags, Scaleway `qwen3.8-27b`), `title` (OCR text → title, Scaleway `mistral-small-3.2-24b-instruct-2506`, document-type- and correspondent-aware), `mark_done` (adds the `archivlotse-done` tag, no AI, only if no earlier step in the run failed). Most of the rest of the concept doc (custom fields beyond single-value text/number types, general long-document handling, queueing, `quality_check: ai_judge`) does not exist yet. Treat the rest of this file as the target architecture, not current state, and update this section as more steps/capabilities land.

## Commands

```bash
# Install (editable; also registers the `archivlotse` console script)
pip install -e ".[dev]"

# Run tests
pytest

# Run a single test
pytest tests/test_pipeline.py::test_process_step_is_idempotent_and_audits_only_on_change

# Run one config-defined step for a Paperless document (needs config/paperless.yaml + config/ai.yaml)
archivlotse process 6023 --step title --dry-run
archivlotse process 6023 --step title
archivlotse process 6023 --step title --model llama-3.3-70b-instruct  # override the model from config/steps.yaml
archivlotse process 6023 --step document_type --dry-run --verbose  # also logs the full prompt + raw AI answer at DEBUG
archivlotse process 6023 --step title --force  # bypass step/candidate caches, recompute even if input unchanged

# Run the whole pipeline (config/steps.yaml: pipeline:) for one document
archivlotse process 6023 --dry-run
archivlotse process 6023

# Batch mode: run the jobs from config/batch.yaml (tag/title-regex filters,
# optional step subset) - does NOT add/remove any tag itself
archivlotse batch --dry-run
archivlotse batch scan_titles --limit 10

# Server mode: webhook (POST /process) + batch jobs with cron: (needs ARCHIVLOTSE_WEBHOOK_TOKEN)
ARCHIVLOTSE_WEBHOOK_TOKEN=secret archivlotse serve --port 8080
docker compose up -d --build   # same, in Docker (see docker-compose.yml, .env.example)

# Wipe all cached step results + candidate lists (NOT the audit log)
archivlotse clear-cache
```

End users who don't want a dev install can still run the same thing as `python -m archivlotse.cli process ...` from the repo root without `pip install -e .` (only the runtime deps need to be present). See `README.md` for the beginner-oriented setup walkthrough (venv, config, troubleshooting) — keep that in sync with CLI/config changes made here.

Local config: copy `config/paperless.example.yaml` → `config/paperless.yaml` and `config/ai.example.yaml` → `config/ai.yaml` (both gitignored — they hold secrets; values can reference env vars as `${VAR_NAME}`, expanded via `os.path.expandvars` before YAML parsing). `config/steps.yaml`, `config/batch.yaml` and `config/prompts/*.j2` hold no secrets and are committed as-is — deliberately kept OUTSIDE the `archivlotse` Python package and resolved relative to the current working directory (default `"config/prompts"`, see `archivlotse/prompts.py`), same as the other config files, so prompts/step rules can be edited in a deployment (e.g. a mounted volume in Docker) without rebuilding/reinstalling the package. SQLite state defaults to `data/archivlotse.db` (gitignored, created on first run; `archivlotse/db.py` auto-migrates an older schema in place on open, so existing local audit history survives schema changes).

## Implemented so far (`archivlotse/pipeline.py`)

Config layering, in the order it's read:

1. **`config/steps.yaml`** (`archivlotse/steps.py`, committed, no secrets) — a top-level `pipeline:` (ordered step names) plus `steps:` entries, each with: `source_field`/`target_field` (Paperless fields read/written), `condition` (optional skip rule), and either (a) `prompt` + `model` + pre-/post-processing (`preprocessing.max_input_chars`, `postprocessing.strip_quotes`/`max_length`) for text/choice/multi-choice steps, optionally with `candidates_endpoint` (makes it a choice step; the prompt additionally receives `{{ candidate_names }}`) and `multi: true` (makes it a multi-choice step, for a many-to-many field like `tags`), (b) `ocr: {model, timeout}` for the OCR step (`model` names an `ai.yaml` model, Docling included; the old step-level `quality_check`/`docling` keys are rejected with a migration error), or (c) `prompt_step2` + `model_step2` + `fuzzy_assign_min_score`/`fuzzy_assign_min_gap`/`fuzzy_review_min_score`/`fuzzy_candidate_limit` for the correspondent step. `load_step_config` validates which fields are required per shape. `archivlotse/pipeline.py` has no hardcoded knowledge of "title", "document_type", "tags", or any other field/step — it's all read from here.
2. **`config/ai.yaml`** (`archivlotse/config.py: load_ai_config`/`load_ai_models`, gitignored) — two sections: `providers:` (connection details once per backend — for `scaleway`, `access_key_id` + `secret_key`, matching the labels in Scaleway's IAM console; only `secret_key` is actually used, as the Bearer token for the Generative APIs, `access_key_id` is carried through for reference only) and `models:` (model name → `provider` + optional `price_per_1m_input`/`price_per_1m_output`; the key is sent to the provider as the model name unless the entry overrides it with `model:`, for the same model on two providers). Steps in `steps.yaml` reference these model names directly via `model:`/`model_step2:` — there are no logical "roles" any more. The old `roles:` format is rejected with an explicit migration error. Multiple models can share one provider/credentials. `--model` on the CLI overrides the model named in `steps.yaml` (single-step mode only).
3. **`config/paperless.yaml`** (gitignored) — Paperless `url` + `token`.

Processing (`process_step` in `archivlotse/pipeline.py`) dispatches on `step_config.ocr_model`, then `step_config.add_tags`, then `step_config.custom_field`, then `step_config.date_prompt_small`, then `step_config.prompt_step2`, then `step_config.candidates_endpoint and step_config.multi`, then `step_config.candidates_endpoint`:

- **Text steps** (`_process_text_step`): fetch the document, resolve `document_type_name` (`_resolve_document_type_name`, via the cached `_get_candidates(conn, paperless, "document_types")`), skip if `_condition_met()` fails, render the prompt (`input_text` + `document_type_name`), call the AI, clean up the raw output (`_postprocess`), write it verbatim to `target_field`.
- **Choice steps** (`_process_choice_step`): same condition/document-type-name handling (reusing the already-fetched candidates list when the step itself *is* `document_types`, to avoid a duplicate lookup), then fetches candidates via `_get_candidates(conn, paperless, step_config.candidates_endpoint)` (cached; underlying fetchers in `CANDIDATE_FETCHERS`: `"document_types"` → `list_document_types()`, `"tags"` → `list_tags()`, both paginated). The prompt gets the candidate names; a cleaned-up AI answer is matched case/whitespace-insensitively against them. An answer equal to the `UNBEKANNT` sentinel, or one that matches no candidate, is **not** written to Paperless (logged as info/warning respectively, no audit entry). A match writes the candidate's **id** to Paperless (`target_field` expects an FK id, not a name) but logs/audits the human-readable name.
- **Multi-choice steps** (`_process_multi_choice_step`): same condition/document-type-name/candidate-fetch handling, plus the prompt also gets `{{ current_tag_names }}` (the field's current values, by name) so the AI can reconsider them, not just add new ones. The (line-preserving) cleaned answer (`_clean_multiline`, NOT `_postprocess` — that collapses newlines, which would merge the two labeled lines into one) is parsed by `_parse_add_delete_lines()` into an add-part and a delete-part from `"Hinzufügen: ..."`/`"Löschen: ..."` lines (falling back to treating the whole answer as the add-list if neither label is found, for backward compat with a plain comma-list answer); each comma-separated entry in both parts is validated independently against the candidates (case/whitespace-insensitive, `NONE_SENTINEL` "KEINE" meaning an empty list) — an unmatched entry is logged as a warning and dropped, not fatal. The final value written is `sorted((set(current_ids) | add_ids) - delete_ids)` — existing values are kept unless explicitly deleted; if a candidate is in both lists, delete wins (logged). Since current tag state is now part of the prompt, it's also part of the fingerprint (`current_tags_signature`) — a step run that itself changes the field (e.g. adds a tag) correctly invalidates the cache for the next run, since the prompt input genuinely changed. The audit log gets comma-joined human-readable names for both old and new (`_apply_value`'s `write_value` is the raw id list, the display `old_value`/`new_value` are the names).
- **OCR step** (`_process_ocr_step`): no condition/document-type-name handling (not needed). Decides by the document's `mime_type`: `application/pdf` → `PaperlessClient.download_original` (`?original=true` — without it Paperless serves the archived PDF/A, which already carries its own OCR layer) and `analyze_pdf`, skip unless `needs_ocr`; `image/*` → `download_archive`; anything else → skip. Sends the PDF via `ocr_pdf` of the client `build_ocr_client` picks by provider type: `DoclingClient` (`docling` → `POST /v1/convert/file`, `to_formats=text`, `force_ocr=true`; a non-success status raises `ServiceError` with Docling's per-page errors; no token usage, counted as $0 via `LOCAL_PROVIDERS`) or `OpenAICompatibleClient` (`scaleway` → `{"type": "file", "file": {"file_data": "data:application/pdf;base64,..."}}` as the only message content, no prompt; `finish_reason == "length"` raises `ServiceError` rather than writing a truncated text), both built with `ocr.timeout` (default 600 s) instead of the provider's. The raw markdown answer is cached; `_clean_ocr_text` (applied on every use, so changing it needs no re-OCR) drops `![image](...)` placeholders and flattens LightOnOCR's HTML tables to one `cell | cell` line per row. Not written if empty or shorter than `MIN_OCR_LENGTH_RATIO` (0.3) × the existing text — a post-OCR safety net against fragments, not a pre-check. Audit `old_value`/`new_value` are `"[N Zeichen, <sha256[:8]>]"` summaries (`_apply_value`'s `write_value` vs. display-`new_value` split). Cache semantics differ from other steps: the fingerprint is sha256(PDF bytes) + provider + model (the current text is deliberately not part of it, else writing the result would invalidate the cache and re-OCR — and re-pay — on every run). A cache hit is applied unless `db.field_written_since` finds an audit-log write of `content` after the cached result was created *and* the text now differs — i.e. someone corrected it by hand in Paperless; that is never overwritten except by `--force`. A cached result from a `--dry-run` is still applied by the next real run.
- All shapes share `_apply_value()`: compares old vs. new, skips on no-op or `--dry-run`, otherwise calls `update_document_field` (type hint now `int | str | list[int]`) + `append_audit_log`.
- **Idempotency:** before calling the AI/OCR model, computes a SHA-256 fingerprint (`_fingerprint(*parts)`, variadic) over the relevant inputs (truncated text, prompt version, provider/model, postprocessing settings, candidate list for choice/multi-choice steps, or the PDF bytes' hash for the OCR step) and checks it against the `step_results` SQLite table (keyed by `step_name` + `document_id` + fingerprint); a hit skips the AI/OCR call entirely.
- **Candidate caching:** `_get_candidates()` checks `candidate_cache` (SQLite: `endpoint` PK, JSON `data`, `fetched_at`) via `db.get_cached_candidates`/`save_candidates` before calling a `CANDIDATE_FETCHERS` entry; a hit within `CANDIDATE_CACHE_TTL_SECONDS` (2h) skips the Paperless call entirely — verified live that a second `archivlotse process` run makes zero `/api/tags/`or `/api/document_types/` requests. To force a refresh sooner, delete rows from `candidate_cache` directly (no CLI flag yet).
- **Audit log:** the separate `audit_log` SQLite table (`document_id`, `field_name`, `old_value`, `new_value`, `changed_at`) only ever gets a row when a field is actually written to Paperless — never on cache hits, no-op, rejected choice suggestions, skipped conditions, an OCR step skipping a born-digital PDF, or `--dry-run`.
- **Temperature:** every AI call is sent with `archivlotse/ai/base.py: TEMPERATURE` (0.0, deliberately global, not configurable): OpenAI-compatible `temperature`, Ollama `options.temperature`. All steps are extraction/classification tasks where the same input should give the same answer; a provider default (~0.7) made e.g. an invoice amount flip between runs. Not part of step fingerprints, so results cached before this change stay cached until `--force`/`clear-cache`.
- **Cost tracking:** `archivlotse/ai/base.py: AIResult(text, prompt_tokens, completion_tokens)` is what both `OllamaClient.generate()` (from Ollama's `prompt_eval_count`/`eval_count`) and `OpenAICompatibleClient.generate()` (from the OpenAI-style `usage.prompt_tokens`/`usage.completion_tokens`) return now, instead of a bare string. `_estimate_cost(ai_config, prompt_tokens, completion_tokens)` returns `0.0` unconditionally for `provider == "ollama"` (local = free), `None` if usage data or `AIConfig.price_per_1m_input`/`price_per_1m_output` (from the role in `config/ai.yaml`) aren't available, else the computed USD estimate. `_log_usage()` logs it and every non-OCR step passes it to `save_step_result(..., prompt_tokens=, completion_tokens=, estimated_cost_usd=)`, persisted in `step_results` (migrated in place for older DBs via `_migrate_step_results_usage_columns`). Not implemented: aggregating/reporting total cost (e.g. per document or per month) — only per-call, queryable via `SELECT SUM(estimated_cost_usd) FROM step_results`.
- `--dry-run` runs the full step (including any AI/OCR call and `step_results` caching) but skips the Paperless `PATCH` and the audit log entry.
- `--force` (threaded through `process_pipeline`/`process_step` into each `_process_*_step` function) makes every cache lookup (`get_cached_step_result`, `_get_candidates`) a guaranteed miss, forcing a fresh AI/OCR/Paperless call even if the fingerprint is unchanged. It deliberately does **not** bypass business-rule skips (a step's `condition:`, or the OCR step's "PDF already has real text" skip) — those aren't caching. `save_step_result` is an upsert (`INSERT ... ON CONFLICT ... DO UPDATE`) specifically so a `--force` recompute with an unchanged fingerprint overwrites the existing row instead of violating the `UNIQUE (step_name, document_id, fingerprint)` constraint.
- `archivlotse clear-cache` (`archivlotse/db.py: clear_caches`) empties `step_results` and `candidate_cache` entirely, in one shot (no per-step/per-document granularity) — for when Paperless metadata (e.g. tags) was reorganized and stale cached suggestions shouldn't linger until their TTL/fingerprint naturally expires. Never touches `audit_log`.

`process_pipeline` loads `pipeline:` via `load_pipeline_order` (or takes an explicit `step_names` subset, used by batch jobs) and calls `process_step` for each name in order; a step with `requires_previous_success: true` (e.g. `mark_done`) is skipped if any earlier step in the same run raised. Each step is run catching and logging (not re-raising, via `archivlotse/errors.py: log_failure` — expected failures like `httpx.HTTPError`/`ServiceError` as one ERROR line with method+URL, traceback only at DEBUG/`--verbose`; anything else with full traceback; the CLI top level does the same for `ValueError`/`FileNotFoundError` config errors and exits 1) any exception per step so e.g. a failing OCR call doesn't block `document_type`/`title`. Each step still does its own fresh `paperless.get_document()`, so a later step sees an earlier step's actual Paperless write — except in `--dry-run`, where nothing is written, so later steps keep seeing pre-pipeline state (documented caveat, not a bug).

`archivlotse batch [job ...] [--limit N] [--dry-run] [--force]` (`archivlotse/batch.py: process_batch`) is the only multi-document entry point — `archivlotse process` takes exactly one document id. Jobs live in **`config/batch.yaml`** (committed, no secrets; `load_batch_jobs`, run in file order, or only the named ones): `filter.tags` (all required, by name), `filter.exclude_tags` (none allowed; a tag that doesn't exist in Paperless yet is warned about and excludes nothing, whereas an unknown required tag is an error), `filter.title_regex` (one regex or a list, any may match; `re.search` on the title, applied locally since Paperless has no regex filter), `filter.document_types` (any may match, by name, server-side `document_type__id__in`), `filter.missing_custom_fields` (all named custom fields must be absent or valueless) / `filter.filled_custom_fields` (all must have a value) (both checked locally from the listed `custom_fields` rather than via Paperless's version-dependent `custom_field_query`; unknown document types/custom fields are errors; all names resolved into a `ResolvedFilter`), optional `steps:` (subset/order passed to `process_pipeline(step_names=...)`, default the whole `pipeline:`) and `limit:` (CLI `--limit` overrides). A job needs at least `tags`, `title_regex` or `document_types` so it can't silently match the whole archive; all job and step names are validated before any document is touched. Tag criteria go to Paperless server-side (`PaperlessClient.list_documents(tags_all=, tags_none=)` → `tags__id__all`/`tags__id__none`, with `fields=id,title,tags,document_type,custom_fields` so listing ~8000 documents doesn't pull every OCR text); ids are processed ascending. Immediately before each document it's re-fetched and re-checked against the full filter (`_matches`) — one that no longer matches (tag removed mid-batch, title already rewritten by an earlier job in the same run) is skipped. A document that raises is logged and skipped. Deliberately does **not** add or remove any tag itself (e.g. setting `archivlotse-done`) — that's a separate decision, not assumed here.

**Server mode** (`archivlotse serve`, `archivlotse/server.py`, stdlib `http.server` only, no web framework): one `Worker` thread runs every task strictly sequentially from an in-memory queue (deduped by key while still waiting; lost on stop — by design, the cron'd `todo` job catches up documents without `archivlotse-done`); a `Scheduler` thread queues batch jobs whose `cron:` (`archivlotse/cron.py: CronSchedule`, own 5-field parser + `@daily`-style aliases, local time/`TZ`, cron's dom-OR-dow rule; read once at start, missed minutes caught up to `MAX_CATCH_UP_MINUTES`) matches, as `process_batch(job_names=[name])`; `POST /process` (alias `/webhook`) authenticates `ARCHIVLOTSE_WEBHOOK_TOKEN` (Bearer or `X-Archivlotse-Token`, `hmac.compare_digest`; server refuses to start without one), takes `document_id`/`doc_id`/`id` or `doc_url` (id parsed from `/documents/<id>/`, which is what Paperless workflow webhooks offer) plus optional `steps`/`step`, `dry_run`, `force` from query, JSON or form body, validates step names, answers 202 and queues `process_pipeline(step_names=...)` after a per-document `check_services` (service down → document skipped, logged). `serve --dry-run` forces dry-run for everything. `GET /health` for the Docker healthcheck. `archivlotse batch` ignores `cron:`. Docker: `Dockerfile` (entrypoint `archivlotse`, default `serve`, UID 1000, tzdata), `docker-compose.yml` (mounts `./config:ro` + `./data`, `.env` from `.env.example`, bundled `docling` service → `ai.yaml` needs `base_url: http://docling:5001` inside compose).

**Preflight** (`archivlotse/preflight.py: check_services`): `archivlotse process` (CLI) and `process_batch` refuse to start, raising one `ServiceError` listing every problem, unless Paperless and the AI/OCR service of every model the steps to run are configured with (`model`, `model_step2`, `ocr.model`, or `--model`) respond and offer that model, also with `--dry-run`; `clear-cache` is not checked, and neither is `process_pipeline`/`process_step` when called directly (a batch would otherwise re-check per document). Decided from config alone, not per document: Docling counts as needed for the `ocr` step even if the PDF turns out not to be a scan or a result is cached. Each client has a `check()` hitting only a free endpoint with `CHECK_TIMEOUT` (10 s): Docling `GET /health`, Ollama `GET /api/tags`, OpenAI-compatible `GET /models`, Paperless `GET /api/profile/` (not `/api/tags/`, which takes ~13 s on the live archive). It only covers the start: a service that dies mid-batch still fails per step/document as before.

**OCR decision history:** a `wordfreq`-based text-quality heuristic used to gate re-OCR via Docling. It was removed on 2026-10-26 because it couldn't separate garbled from fine numeric-heavy documents — a Kontoauszug with garbage OCR scored 0.53, the same statement perfectly transcribed only 0.62 — so it skipped exactly the documents that needed OCR. Don't reintroduce a quality metric as the gate; the scan/no-scan structure check replaced it by the user's explicit choice.

Adding the next **text**, **choice**, or **multi-choice** step for `document_types`/`tags`/`correspondents` is pure config: a new `.j2` prompt in `config/prompts/`, a new entry under `steps:` (and `pipeline:`) in `config/steps.yaml`, and a matching entry under `models:` in `config/ai.yaml` if needed — no changes to `pipeline.py`. A choice/multi-choice step against a *different* Paperless list needs one small code change: a new entry in `CANDIDATE_FETCHERS` (and a `PaperlessClient.list_x()` method if one doesn't exist yet). Another **custom field** of type string/longtext/integer/float/monetary is pure config too (a `custom_field:` step, see above); `select`/`date`/`boolean`/`documentlink`/`url` fields need a new branch in `_parse_custom_field_answer` first (e.g. `select` must map a label to its option id). Steps needing multiple input fields or multi-field output (e.g. future `document_date`, `invoice`/`bank_statement` extraction steps from the concept doc) will need more substantial changes to `pipeline.py`, not just config, following the pattern of the correspondent step (`_process_correspondent_step`), which is itself a fifth, fully bespoke shape rather than config on top of the generic four.

## What ArchivLotse is

ArchivLotse is a configuration-driven AI assistant that post-processes documents in Paperless-ngx: improving classification, generating meaningful titles, and extracting metadata — without sending every available piece of information to a large language model for every document. Paperless-ngx remains the single source of truth; ArchivLotse never replaces it or duplicates the document archive.

Guiding principle: **as little AI as necessary, as much traceability as possible.** Use deterministic rule-based logic wherever rules are sufficient; use language models only where document content must be interpreted. The AI proposes, the software validates, Paperless stays authoritative.

## Core architecture

**Separation of code and business rules.** Python provides execution logic, API clients, and validation. All domain-specific behavior lives in two kinds of config, not in Python:

- **YAML files** define: available AI providers/models, pipeline steps and their order/conditions, document-type descriptions and selection criteria, tag meanings, correspondent name variants/matching rules, document-type-dependent custom fields, document-date determination rules, token/cost budgets and escalation rules, and validation/approval conditions. Existing tags, document types, correspondents, and custom fields are loaded from the Paperless API by ID — the YAML only adds business-level descriptions/rules on top, never duplicates IDs.
- **Jinja2 templates** (one per AI task, versioned): `classify.j2`, `title.j2`, `document_date.j2`, `correspondent.j2`, `tags.j2`, `bank_statement.j2`, `invoice.j2`, `custom_fields.j2`, etc. Each prompt receives only the document information, rules, and candidates relevant to that specific task — not the full document/metadata set.

**Multi-stage processing pipeline** (independently runnable steps), chosen per document rather than always run in full:

1. **Document check & OCR** — detect whether usable text/embedded text already exists, whether the PDF is scanned, page count, and signs of bad OCR. OCR is invoked only when it would actually help. The original file is never modified; improved OCR text is written back to Paperless only after a quality check.
2. **Coarse classification** — a small, cheap model assigns a broad category (invoice, bank/credit-card statement, contract, government letter, certificate, insurance, general correspondence, unknown). This determines which further analyses run, and need not map 1:1 to a final Paperless document type.
3. **Targeted metadata extraction** — depends on the category from step 2 (e.g. bank statements get bank/correspondent/period/IBAN extraction; invoices get issuer/invoice number/date/amount/currency). Steps irrelevant to the detected type are skipped entirely.
4. **Validation & approval** — proposed tags/document types must actually exist; IBAN checksum validation; preserve leading zeros in account numbers/IDs; plausibility-check dates and amounts; verify a value is actually evidenced by the OCR text; detect contradictory/ambiguous results; never overwrite existing correct metadata. Uncertain proposals are flagged for manual review rather than auto-applied.

**Candidate pre-selection instead of bulk context.** For large metadata sets (e.g. 500+ correspondents), ArchivLotse does local candidate search first (exact match, known abbreviations/spelling variants, RapidFuzz fuzzy matching, known email domains/addresses) and only sends the LLM a short candidate list when the match is ambiguous — never the full list. Same principle for tags and document types. New tags/document types/correspondents are never created without authorization.

**Long-document handling** is a deliberate three-tier strategy, not "always send full text": short documents get full-text analysis; medium documents get section selection by headings/keywords/structure; long documents are first searched for relevant passages (stored with page/position references) which are only passed to the LLM on demand. This matters especially for document-date determination, since the governing date may appear anywhere in the document (e.g. next to a signature or in an addendum) — the pipeline must not assume the first page is sufficient.

**Pluggable AI providers via logical model roles**, not hardcoded provider calls. Config defines roles like `fast` (cheap classification/titles), `precise` (complex extraction/date decisions), `fallback` (second pass on unclear results). The pipeline picks a role based on document type, text length, task complexity, and validation outcome — not a fixed provider. Planned providers: Ollama (local), Scaleway Model-as-a-Service (EU cloud), and other OpenAI-compatible APIs via a common interface. Sensitive documents can be restricted to local-only processing; external providers should receive only the text excerpts/metadata actually needed.

**Audit logging and incremental processing.** Every processing step is logged: document ID, timestamp, pipeline/git version, step, model+config, prompt version, result, validation status, affected Paperless fields, old vs. proposed vs. actually-applied values, errors/retries, token usage, and estimated cost. This audit log is kept separate from n8n/AI-service logs. Each step also has its own status and a fingerprint of its relevant inputs, so that changing one template/rule (e.g. the document-date prompt) does not force re-running unrelated unaffected steps (e.g. OCR, classification) — this keeps reprocessing large archives cheap.

## Intended CLI shape

```bash
archivlotse process 6023 --dry-run          # implemented: whole pipeline
archivlotse process 6023 --step title       # implemented: single step
archivlotse process 6023 --step document_date  # implemented
archivlotse batch todo --limit 10             # implemented: batch jobs from config/batch.yaml
archivlotse serve                               # implemented: webhook + cron'd batch jobs (Docker default)
archivlotse status 6023                         # not implemented
archivlotse audit 6023                          # not implemented (query data/archivlotse.db directly for now)
```

`--dry-run` is a first-class mode: runs all analyses/validations without writing any metadata back to Paperless. Production operation is meant to add a persistent queue, retries, and resumable jobs — this is explicitly Phase 3, not required for a prototype.

## Explicit non-goals

Do not design toward: replacing Paperless-ngx as the DMS, permanently duplicating original documents, building a full separate document archive, creating new tags/document types without authorization, silently overwriting uncertain AI results, becoming a general-purpose agent framework, or requiring a full web application.
